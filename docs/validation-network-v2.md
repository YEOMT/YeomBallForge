# 교실 세션·WebSocket 검증 v2

**2026-11-25 12:19 UTC, Linux x64 / Node.js v24.22.3에서 학생 30명과 호스트 1명의 실제 WebSocket으로 4판을 완료했습니다.** 정원 초과 거절, 전투 중 재접속, 새 강화 선택 규칙, 호스트 1경기 방송, 학생 자신의 토너먼트 경기, 럼블 개인 요약, 최종 결과 수신, 재경기 초기화를 검사했습니다.

검사 코드: [tools/socket-load.js](../tools/socket-load.js). 원시 실측 JSON은 로컬 `artifacts/socket-v2.json`이며 `artifacts/`는 Git에서 제외됩니다. 아래 표는 해당 실행의 값을 옮긴 것입니다. 예전 [네트워크 검증](validation-network.md)의 과거 수치와 다른 규칙·운영체제·코드이므로 단순한 성능 향상 비교로 해석하면 안 됩니다.

## 재현

```sh
npm ci
mkdir -p artifacts
node --expose-gc tools/socket-load.js > artifacts/socket-v2.json
```

도구는 임의의 루프백 포트에 실제 서버를 띄우고 개별 WebSocket 31개를 연결합니다. 서버와 클라이언트가 같은 Node 프로세스를 사용합니다. 모든 학생이 8문항을 맞혀 **10 + 8×2 = 26장**을 받고, 실제 강화·경로 선택·티어별 볼 선택·출전 확정 명령을 보냅니다. 출전 빌드를 서버 내부에 직접 주입하지 않습니다.

같은 방에서 **토너먼트 → 럼블 → 복합 → 럼블**을 진행합니다. 각 판의 실측 구간은 실제 시계로 약 4.3~4.4초입니다. 호스트가 약 360ms 간격으로 12번 관전 경기를 선택하고, 응답 화면에 그 경기 1개가 오는지 확인합니다.

실측 후에는 실제 서버 runner의 시간 입력만 가속합니다. 전투 규칙과 고정 60Hz 시뮬레이션은 그대로 실행하며, 서버가 직접 결과 단계로 전환해 **30명의 클라이언트가 모두 RESULTS를 수신한 뒤** 재경기를 요청합니다. 가속 구간은 아래 처리시간·전송량·왕복시간에 포함하지 않습니다.

## 발견한 요약 전송 문제와 수정 확인

초기 도구가 실패한 원인은 단순히 학생의 렌더링 프레임이 적어서가 아니었습니다. 럼블 학생은 시뮬레이션을 받지 않고 개인 요약을 받는데, 서버가 **1초 요약 타이머를 갱신한 뒤 그 시점이 80ms 전송 프레임과 겹치지 않으면 요약을 보내지 않는 문제**가 있었습니다.

수정 전 진단 실행의 네 번째 럼블에서는 기존 약 1.4초 측정창 동안 서버 전투 tick 처리 87회, 호스트 프레임 20개가 있었지만 학생 30명은 모두 개인 요약 0개였습니다. 서버에서 `summaryDue`를 실제 전송 프레임과 함께 판단하도록 고쳤습니다. 수정 후 아래 두 럼블에서 학생마다 요약을 4회 받았고, 연속 개인 요약의 최대 간격은 약 1.05~1.07초였습니다.

검사 도구도 보강했습니다. 럼블 학생에게 최소 2회 이상의 주기적 개인 요약이 오는지와 최대 간격 2초 미만을 검사합니다. 완료를 동기적으로 건너뛰고 바로 재경기하던 방식 대신, 실제 runner가 결과를 송신하도록 가속하여 최종 등수와 처치자 필드까지 클라이언트에서 대조합니다.

## 실시간 처리와 전송량

복합 모드의 **실시간 측정 구간은 토너먼트 단계**입니다. 이후 토너먼트·럼블 완료와 최종 개인 결과는 가속 구간에서 검증했습니다. 따라서 복합 모드 전체 경기 시간이나 복합 럼블 단계의 실시간 전송 성능을 측정한 표는 아닙니다.

| 실시간 측정 | 4.41초 | 4.34초 | 4.43초 | 4.33초 |

`tick 처리`는 시뮬레이션이 실제로 전진한 `room.tick()` 호출의 처리시간입니다. 한 호출이 여러 고정 시간 단계를 처리할 수 있고, JSON 직렬화와 소켓 전송 비용은 이 시간에 포함하지 않습니다.

RTT는 명령을 보낸 시점부터 서버의 승인 응답을 받을 때까지입니다. 호스트 프레임 수에는 주기 스냅샷과 `watch` 명령의 즉시 응답이 함께 들어 있으므로 주기 스냅샷 전송률 자체와 같지 않습니다. 수신량은 TCP 소켓에서 읽은 바이트이며 상태·명령 응답·전투 패킷을 모두 포함합니다.

## 해석 범위

이 결과는 현재 규칙으로 **한 방의 30명 참가·재접속·결과·재경기와 역할별 전송 경로가 로컬 실제 소켓에서 동작했다는 근거**입니다. 공유 실행환경의 같은 프로세스와 루프백을 사용했으므로 다음 항목은 이 결과로 보장하지 않습니다.

- 학교 무선망의 지연·끊김·패킷 손실, 원격 서버까지의 인터넷 경로, TLS 비용.
- 학생 휴대전화나 교실 PC의 Canvas 렌더링 프레임률과 발열.
- 여러 교실이 동시에 여는 다중 방의 서버 수용량.
- 수 시간 운영 시의 메모리 안정성. 네 번의 GC 후 힙 표본은 장시간 누수 검사가 아닙니다.
- 전체 전투를 실제 시간으로 끝까지 재생했을 때의 성능. 완료 구간은 기능 검증을 위해 가속했습니다.

강화 난수와 전투 시드가 매번 달라져 볼 구성·경기 길이·패킷 크기도 달라집니다. 위 값은 단일 실행의 실측값이며 서비스 수준 보장이나 학교 현장 벤치마크로 제시하지 않습니다.
