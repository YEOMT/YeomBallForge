# 전투 규칙 2: 기믹·개인 관전·부하 검증

2026-11-25 · 규칙 버전 2 · Linux x64 · Node.js v24.22.3

이 문서는 역순 티어와 신규 12개 전투 기믹을 반영한 버전의 검증 기록이다. `validation-combat.md`에 있는 규칙 버전 1의 승률과 성능 수치를 신규 26종에 그대로 적용하면 안 된다.

## 서버와 개인 럼블 화면의 계약

`apps/server/room.js`, `apps/server/index.js`의 프로젝션을 읽기 전용으로 리뷰했다. 8명으로 실제 `Room`을 만들고 `combined` 전체를 `stepCompetition`으로 실행하면서 각 틱의 학생 프레임을 검사했다. 이 점검은 인메모리 서버 모델과 전투 엔진 간 계약 검사이며 실제 교실 네트워크 측정은 아니다.

| 항목 | 확인 결과 |
| --- | --- |
| 토너먼트 | 호스트에게 선택한 전장 한 개를 전달한다. 학생의 자기 경기가 진행 중일 때는 다른 경기 선택보다 자기 경기를 우선한다. |
| 럼블 전환 직후 | 호스트 전장 한 개, 학생 `arenas: []`, `matches: []`, `bracket: []`를 반환한다. 학생 개인 HP와 생존 상태는 새 럼블의 상태이다. |
| 사망 후 개인 상태 | 6,558개의 사망 후 개인 프레임에서 엔진의 `rank`, `alive`, `killedById`, `killedByName`과 일치했다. 이 실행의 럼블은 2,250틱에 끝났다. |
| 결과 및 재접속용 state | 학생의 `results.rumble`은 본인 한 행이고, `state.room.battle`도 개인 요약이다. 호스트는 전체 결과를 받는다. |
| 캐시 분리 | 럼블 개인 패킷의 캐시 키에 학생 ID가 들어가며 다른 학생의 요약과 공유하지 않는다. |

생존 중 엔진의 `rank`는 **0 = 아직 미확정**이다. 서버의 학생 개인 요약은 이를 `null`로 정규화한다. 개인 UI는 최종 순위가 정해졌을 때만 표시하므로 `0위`로 표시하지 않는다.

연속 모드의 단계 변경 자체는 `Room.tick()`의 dirty 신호를 만들지 않는다. 따라서 학생에게 토너먼트에서 럼블로 바뀐 요약이 도착하는 시점은 다음 정기 요약까지 최대 약 1초 늦을 수 있다. 전환 이후 전장 프레임을 학생에게 보내는 코드는 차단되어 있다. 이 지연을 더 줄이려면 stage 변경을 상태 갱신 이벤트로 처리할 수 있다.

## 30인 전투 부하 측정

### 환경과 방법

- 실행 환경에 노출된 CPU 모델은 AMD EPYC 7763 64-Core Processor이며, 사용 가능한 논리 CPU는 9개였다. JS 전투 루프는 한 Node 프로세스에서 순차 실행했다.
- 각 시나리오별 600틱을 먼저 실행한 후 새 전장으로 **7,200틱 = 120초치**를 측정했다. 고정 시드는 `982451653`이다.
- 모두 내부 `level: 19`, 즉 **T1**, 참가자 30명이다. 개별 볼 변형 보정은 사용하지 않았다. 혼합 조합은 `Object.keys(CLASSES)`의 26종을 순환하여 30명을 만든다.
- 탈락으로 부하가 줄지 않도록 현재 HP만 1,000,000으로 올렸다. 원래 `maxHp`, 공격력, 쿨다운과 이동 규칙을 유지하므로 분노 계산의 분모는 바뀌지 않는다. 압박과 경기 종료는 측정 중 비활성화했다. 45초부터 시작하는 실제 럼블 전장 축소는 유지했다.
- `performance.now()`로 `stepArena()` 한 번만 감쌌다. 계측용 집계와 스냅샷 생성 시간은 전투 틱 시간에서 제외했다.
- 매 5틱마다 `arenaSnapshot()`과 `JSON.stringify()`를 별도로 측정했다. 전송 패킷 전체, 소켓 쓰기와 압축은 포함하지 않았다.
- 모든 틱에서 좌표·속도·HP가 유한수인지, 전역 및 주인별 공격체 제한을 넘지 않는지 검사했다. 전체 시나리오에서 30명이 끝까지 생존했다.

### 물리·기믹·피해 계산

단위는 ms/틱이다. 60Hz 한 틱의 시간 예산은 약 16.67ms이다.

상한 시나리오는 정상 볼의 발사 주기를 흉내 낸 대전이 아니다. 매 틱 직전에 30명의 소유자에게 유도탄 네 개씩을 보충하고, 중력장 한 개씩을 유지해 엔진이 항상 최대 허용 공격체 수로 계산하도록 했다. 보충 작업 자체는 측정 구간 밖이다. 각 탄은 실제 유도·sweep 충돌·피해·만료 처리를 거친다.

측정된 일반 조합 중 삼검 30명이 회전 무기 90개를 검사하므로 가장 높은 평균 틱 시간을 보였다. 인위적 상한에서도 이 환경의 측정 p99는 2.056ms 미만이었다. 이것은 해당 실행의 결과이며 다른 서버의 최악 지연을 보장하지 않는다.

전역 상한은 탄환 120개, 필드 30개다. 주인별 상한은 탄환 6개, 필드 3개이며 사역마는 추가로 최대 두 개다. 삼검 등 몸체에 붙은 회전 무기는 `arena.objects`의 발사체가 아니므로 위 탄환 개수에 포함하지 않는다. 이들은 클래스마다 고정된 개수이며 삼검 30명의 경우 90개다. 이벤트 기록은 128개로 제한된다.

소환 30명에서는 전역 필드 30개가 먼저 찼으므로 한 시점에 각자 사역마 한 개씩만 유지되는 구간이 있었다. `최대 두 개`는 혼잡한 전장에서도 두 개가 반드시 보장된다는 뜻은 아니다. 상한을 바꾸려면 성능뿐 아니라 소환 클래스의 상대적 강함도 다시 점검해야 한다.

## 해석과 남은 검증

1. 이 측정에서는 새 기믹이 30인 전투를 60Hz로 계산하는 데 큰 CPU 부담을 만들지 않았고, 발사체가 무제한 누적되는 현상도 없었다. 럼블 전장을 호스트 한 명에게만 보내는 서버 프로젝션과도 맞는다.
2. 브라우저 Canvas, 초상화 디코딩, 실제 화면 FPS, 오디오, 모바일 발열, Wi-Fi 패킷 손실·지연은 이 수치에 포함되지 않는다. 서버가 빠르다고 교실의 관전 화면이 반드시 매끄럽다는 뜻은 아니다.
3. JSON 직렬화 비용은 전투 계산과 별개이다. 호스트에게 보내는 실제 크기는 전장 스냅샷에 대진·상태 메타데이터가 더해진다. 표의 최대 크기는 관측된 단일 스냅샷 크기이며 실제 초당 네트워크 사용량을 측정한 값이 아니다.
4. 타임슬라이스·JIT·GC와 공유 실행 환경의 다른 작업이 특히 최대 지연에 영향을 준다. 한 차례 측정만으로 허용 동시 교실 수나 서버 상품별 수용량을 단정하지 않는다.
5. 신규 기믹의 동작과 상한을 확인했지만 신규 26종 전체의 균형 잡힌 승률을 입증한 것은 아니다. 버전 1의 13종 승률 표를 인용하여 신규 밸런스가 검증됐다고 주장하지 않는다. 실제 수업의 티어·경로 선택 분포를 포함하는 대진별 밸런스 조정이 후속 과제다.

## 측정 재현용 핵심 루프

다음 명령은 동일한 일반 조합 6개의 틱 시간과 공격체 상한을 재측정한다. 출력은 실행 환경에 따라 달라진다. 저장소 루트에서 실행한다.

```sh
node --input-type=module <<'JS'
import {performance} from 'node:perf_hooks';
import {CLASSES, COMBAT} from './packages/content/classes.js';
import {createArena, stepArena} from './packages/sim/index.js';
const ids = Object.keys(CLASSES);
function make(kind, seed) {
  const builds = Array.from({length:30}, (_, i) => {
    const id = kind === 'mixed' ? ids[i % ids.length] : kind;
    return {id:'p'+i, name:'부하'+i, level:19, classId:id, element:CLASSES[id].element};
  });
  const a = createArena(builds, {mode:'rumble', seed});
  a.limitTicks = a.pressureTick = 1e9;
  for (const b of a.balls) b.hp = 1e6;
  return a;
}
for (const kind of ['mixed','summoner','prism','gravity','beam','trinity']) {
  const warm = make(kind, 71);
  for (let i=0; i<600; i++) stepArena(warm);
  const a = make(kind, 982451653), times = [];
  let shots = 0, fields = 0;
  for (let i=0; i<7200; i++) {
    const t = performance.now(); stepArena(a); times.push(performance.now()-t);
    const currentShots = a.objects.filter(o => !o.field).length;
    const currentFields = a.objects.filter(o => o.field).length;
    shots = Math.max(shots, currentShots); fields = Math.max(fields, currentFields);
    if (shots > COMBAT.projectileLimit || fields > COMBAT.fieldLimit) throw Error('상한 위반');
    if (a.balls.some(b => ![b.x,b.y,b.vx,b.vy,b.hp].every(Number.isFinite))) throw Error('비유한 상태');
  }
  times.sort((a,b)=>a-b);
  console.log({kind, p95:times[6839], p99:times[7127], max:times.at(-1), shots, fields});
}
JS
```
